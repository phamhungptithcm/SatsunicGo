# Feedback retention rollout and renewal

This implements the already approved classes, not a continuous erasure SLA. Source/local tests do not prove indexes, Scheduler, policy activation or production deletions.

1. Keep settings/askFeedback new feedback collection inactive until current immutable artifact, exact Function runtime/source, three indexes READY and Scheduler readback are verified. Deploy only through the normal immutable release workflow, with cleanup policy absent/disabled. No rule/TTL or business-data migration is part of this change.
2. Normal release identity must be github-release@satsunicgo.iam.gserviceaccount.com under the exact main release workflow. Root's RETENTION-IAM-METADATA.json shows the direct deployer role lacks datastore.indexes.list/create, while cloudscheduler.jobs.get exists. Do not infer inherited/effective authority. Apply no role expansion without the separately reviewed exact IAM delta. A 403 blocks before Functions/Hosting promotion with RETENTION_INDEX_IAM_DENIED; no bypass or fallback.
3. Review published deployment.json.feedbackRetention and its receiptSha256. It binds exact source SHA/tag/index digest, three READY names, active hourly UTC Scheduler, POST/OIDC target and Function revision. The separate retention-readiness.json is evidence only; CI writes neither activation nor readiness settings. The receipt hash is SHA-256 of the canonical fixed-field payload from retentionReadinessDigest / feedbackRetentionReadinessDigest, excluding receiptSha256; map key order is irrelevant. Runtime recomputes and compares it. Protected settings IAM supplies authority; the checksum is integrity evidence, not authentication.
4. Creating settings/askFeedbackRetentionReadiness or enabling settings/askFeedbackRetention is a separately protected production deletion activation, requiring action-time authority and review. This implementation assignment does not authorize those writes or test deletions. Use only the strict schema in feedback-retention-gate.ts: artifact identity/digest must match, retention remains feedback 1–30 days and technical quota at most 48 hours. Do not relabel/delete legacy or unknown records.
5. Generated readiness expires after 24 hours; strict readiness and activation documents allow at most seven days. Arrange fresh authorized provider readback and reviewed readiness renewal BEFORE expiry, with an alert and operator follow-up. If renewal is not verified in time, disable NEW feedback collection before lapse. The source intentionally does not create automation or extend authority. A one-time activation is insufficient for a 30-day physical erasure assurance.
6. Keep approved cleanup independent of new tester/new feedback admission: turning settings/productionTest or settings/askFeedback off must not prevent existing approved records from expiring while retention policy/readiness remain valid. If retention readiness lapses, cleanup fails closed; quantify backlog and report NOT_READY until renewed. Never claim that expiresAt metadata alone physically erased data.
7. Policy revocation and each class deletion share a serializable transaction read-set. A conflicting disable forces retry and re-admission. Immediately before deletes, wall-clock validity is checked again. At most 100 current eligible rows per class/300 per invocation, three transaction attempts per class, hourly schedule, 60-second HTTP timeout and no retries. A timeout does not prove cancellation of an already committing transaction; expiry can pass during an admitted commit. No instantaneous erasure deadline is promised.
8. Rollback: first disable the protected retention activation policy under authorized operations; retain class/provenance/expiry metadata and all financial/audit data. Restore only a verified immutable artifact. Do not delete indexes/TTL or rewrite legacy feedback during rollback. Root must assess Function removal fences before rolling back to an artifact that still holds cleanup.

Provider operations, activation, protected settings writes and physical erasure are NOT_RUN in this implementation. Scheduled success alone is not evidence that eligible records were erased; use aggregate bounded deletion results, error monitoring and reviewed operational evidence before making a retention SLA claim.
